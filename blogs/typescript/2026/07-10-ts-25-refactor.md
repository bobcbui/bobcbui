从 JavaScript 迁移到 TypeScript，最重要的是控制范围并持续获得类型收益。

![TypeScript 项目渐进式迁移动态示意图](images/07-10-ts-25-refactor.svg)

## 为什么值得理解

渐进迁移到 TypeScript 应持续带来真实类型收益，同时保持产品可发布。优先处理公共边界和高变模块，比一次性改完整仓库更可控。

## 工作原理

allowJs 允许混合阶段，checkJs 可先发现问题；随后为 API、共享工具和核心状态补类型，逐步提高 strict 规则并减少 any 预算。

## 实战场景

旧 JavaScript 项目可先给接口响应加 schema 和类型，再迁移调用最多的工具模块。每个 PR 保持行为测试通过，不同时重写业务逻辑。

## 常见误区

不要用大量 as any 宣布迁移完成，也不要一开始处理最复杂遗留页面。双份类型声明若没有单一来源，会快速漂移。

## 实践清单

- 先迁移高价值公共模块。
- 避免用大量 any 伪装完成迁移。
- 每次迁移都保留行为测试。
- 让静态类型与真实运行时数据保持一致
- 将关键约束纳入类型检查和自动化测试

## 动手练习

选择一个模块建立迁移清单，记录 any 数量和严格检查结果。分三次提交完成边界、实现与调用方迁移，并删除临时兼容层。

## 小结

学习“TypeScript 项目渐进式迁移”时，类型只是表达约束的工具。只有把运行时校验、状态变化和实际构建结果一起验证，才能真正降低错误率，并让类型在需求演进中持续帮助团队。
